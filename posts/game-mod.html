游戏 Mod：从 ARK 修复到增敌定制

一段基于 More Enemies 的修复与玩法调整经历，包含实测反馈、范围收缩和未完成候选。

e.EBee实践回顾 / 006
IN THIS NOTE01 / 兼容性修复02 / 实测反馈03 / 区域与触发04 / 收缩需求05 / 候选状态06 / 性能与回归

我曾用 Codex 协助修复和定制一款现有游戏 Mod：More Enemies。最初要解决的是 ARK 章节的流程问题，后来才扩展到指定区域的增敌设计。

这段经历最值得记录的，是几种结果之间的区别：文件可以解析、离线检查通过、实际游戏流程恢复、整套玩法扩展完成，各自都需要自己的证据。

从已有 Mod 的兼容性问题开始

当时的目标是在保留增敌效果的前提下，排查 ARK 植物 Boss 之后进入方舟的异常。我明确要求先尝试完整保留增敌的修复，再考虑玩法调整。

项目记录中的候选修复只改了两份 ARK 角色池里过期的类型校验值：10 个字段，共 40 字节。敌人数量、位置、生成配置和其他章节保持原状，目的是把兼容性修复的影响范围收窄。

离线检查之后，还有游戏内反馈

那一轮候选记录了 7 项离线测试通过，但交付时仍明确要求从植物 Boss 前的存档验证入口。随后，我在继续优化的会话里反馈：“之前修复没有问题，修复很成功。”

这条反馈支持当时那项修复的游戏内结果；后续新增的敌人、刷新规则和其他章节，仍需要分别检查。不能因为一个入口恢复正常，就把整套 Mod 的稳定性一起算作通过。

增敌需求，要落到区域和触发条件

修复之后，我希望在疗养院、Camp2 营地、桥面、警局周边等指定地点增加敌人，并区分普通怪、特殊怪、首次进入和回访时的体验。

Codex 协助比较了 More Enemies 与 Multiple Enemies 的场景与生成配置。比较过程中反复需要澄清：场景文件里的生成定义数，不等于同时出现在玩家面前的敌人数；不同章节共用的资源，也不能直接按某一段流程整体替换。

需求还涉及过场、任务推进、死亡检查、读档和角色池容量。我关心的不只是“能刷出来”，也包括新增遭遇是否会挡住原有流程。

我后来主动放弃了一部分刷新机制

早期讨论过任务后回访、进入建筑后重复刷新，以及 Camp2 和桥面的持续补刷。随着状态、触发和存档处理越来越复杂，我决定取消 Camp2／桥面的重刷，把这一批收回固定增量；疗养院阁楼返回后的相关尝试另行保留。

桥面的目标也从区域总量调整为按已有新增原点扩为三倍。这不是同一种数量口径，更新要求时必须同步写清楚，避免执行方继续沿用旧目标。

最后一批能核对到的候选

已有归档会话记录了一份独立候选包，范围是选定的 Mod 新增原点：

Camp2 与桥面候选中的配置目标
范围该批候选配置边界
Camp230 只普通＋3 只特殊针对选定新增原点，不含区域全部原版敌人
桥面9 只普通保留原生整组触发，不加入重刷

交付记录列出了 672 项场景检查、44 项回归测试和独立审查通过，同时明确写着：尚未部署或实机验证，整个 Mod 仍未完成。后续的继续请求出现中断；现有记录不足以把这份候选描述成最终完成版。

性能目标还要回到实际游戏

当时我要求保留光追设置，并希望较高密度战斗仍有可接受的帧率。设计讨论因此需要把同屏敌人数、特殊怪、尸体、跨区追击和场景触发一起考虑。

这些讨论没有形成整套扩展稳定达到目标帧率的实测结果。离线场景检查有价值，但它不能代替在指定画质下反复检查战斗、过场、存读档和任务推进。

这次与 Codex 协作留下了什么

我负责给出具体玩法目标、选择取舍和反馈实际体验，Codex 帮助追踪配置关系、比较参考 Mod、制作局部修复与候选，并整理检查依据。

从一次很小的兼容性修复，到后来主动收缩复杂刷新机制，这段经历让我更清楚地看到：在陌生系统里修改行为，要持续核对范围；确认某个阶段成功以后，也要保留后续还没完成的部分。

依据已归档的 More Enemies 修复与定制会话整理。ARK 修复有当时的用户实测反馈；后续 Camp2／桥面候选没有同等实机验证。本文不提供或重新分发原 Mod、游戏资源及候选包。

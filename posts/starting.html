01 / Spotify 相关工作设计

这是我希望整理进个人网站的一段经历。相较于直接列出一个项目名称，我更想把当时的任务、与 Codex 的配合方式，以及真正留下的产物讲清楚。

这一节仍在补充：具体任务过程和成果尚未完成核对，先保留项目主题。后续会补上原始背景、关键步骤和实际结果。

02 / 中日历史原创歌曲对比分析

这次我把 Codex 用在研究型任务里：围绕中日流行歌曲的版本关系，整理发行时间、先行版本、改编关系和来源资料。工作逐渐从查找个别歌曲，扩展到案例表、样本分类、比例复算和完整报告。

在已有记录里，第二轮研究整理到了 34 组歌曲版本案例，并保留了来源和复算材料。比案例数量更值得记下的是，“还没查到先行版本”不能直接当作“已经确认原创”。没有核实清楚的曲目，需要继续标为未确认；某个奖项样本的比例，也不能推成整个时代、整个市场的原创率。

报告后来还做过一次范围调整：把另一项独立论题移出歌曲比较报告，让歌曲版本、统计口径和传播分析留在各自适合的位置。这段经历里，Codex 既参与资料整理，也参与报告生成和检查；我则需要不断明确问题范围、追问证据，并决定哪些内容属于当前研究。

03 / 搭建个人知识库

我希望不同项目和对话之间，能够延续重要的背景、决策和经验。为此，我尝试把 Obsidian 配置成个人知识库，用本地 Markdown 保存资料，让内容能够阅读、修改、检索和追踪。

早期设计采用了三层结构：最上层放稳定规则和入口，中间放摘要、索引与未完成事项，详细项目资料则按需展开。后来又围绕项目、长期领域、资源和归档整理目录，把临时输入与经过整理的知识分开。

一个让我记住的小问题是目录编号：00、01、10、20、30、40、90 并不意味着中间漏建了很多功能，它们只是给未来排序留出空间。为了补齐数字去改名，反而可能让脚本路径和查询失去同步。

另一件事是，目录齐全不等于知识已经积累起来。项目 SOP、原子知识卡片、真实交付材料，都要从后续实践中慢慢提炼。知识库可以先具备可用的结构，再靠实际工作填充内容。

04 / 自动化代码工程工作流

做代码项目时，我也花过不少时间研究怎样和 Codex 协作：从需求分析、PRD，到技术调研、架构设计、计划与代码实现，把阶段、项目状态和交付依据写清楚。

早期工作流尝试过执行与独立验收分开。其中一个真实问题是，验收失败后，Agent 有时会直接留在验收窗口改代码。这样一来，检查的人也开始修改候选结果，原先想保留的独立检查就变得模糊了。这个问题推动了后续对角色职责和交接方式的调整。

另一边，流程本身也需要克制。完全能够自行处理的小事，如果每一步都要求人工确认，会打断工作；而关键架构、权限和项目基线，又确实需要我判断。后续我也尝试过把工作流收窄为五个主要阶段，减少交接负担，同时保留项目事实来自 Git 的原则。

这段经历留下的教训是：流程要服务具体项目。文档和关口应当帮助下一步行动；一旦反而制造重复状态和额外交接，就需要回头简化。
